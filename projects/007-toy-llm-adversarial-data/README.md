# toy-llm-adversarial-data

小規模なTransformerをPyTorchで自作し、**正しい計算ルール・偽の計算ルール・ルールのないランダムなデータを混ぜたとき、モデルの出力がどのように変化するかを検証した実験。**

「LLMに異なるルールのデータを与えると、どのルールに引っ張られるのか？」を、足し算タスクに絞って確認した。

## Overview

今回は、文字単位の非常に小規模なTransformerを構築し、以下の3種類のデータを学習させた。

| 種類       | 例            | 内容                  |
| -------- | ------------ | ------------------- |
| True     | `26+88=114`  | 通常の足し算              |
| Fake     | `26+88=2688` | 足し算ではなく、数字を文字列として連結 |
| Nonsense | `26+88=617`  | 入力とは無関係なランダムな結果     |

True / Fake / Nonsense のデータ割合を変更し、1,000件の入力に対する予測結果から、モデルがどのルールに引っ張られるかを比較した。

## What I tried

* PyTorchによる小規模Transformerの自作
* 文字単位のTokenization / ID化 / Embedding
* Token EmbeddingとPosition Embeddingの利用
* Causal Maskによる次トークン予測
* True / Fake / Nonsenseのデータ割合を変更した学習
* CrossEntropyLossによる次トークン予測
* 学習済みモデルによる1,000件の予測
* True / Fake / Other による結果の分類

## Model

今回のモデルは、Transformer EncoderにCausal Maskを適用することで、Decoder-only型の言語モデルに近い構成として実装した。

```text
Input Characters
       ↓
Token Embedding
       +
Position Embedding
       ↓
Causal Transformer
       ↓
Linear
       ↓
Next Token Prediction
```

### Position Embedding

文字単位の入力では、同じ数字でも「何文字目に存在するか」が重要になる。

例えば、

```text
26+88=114
```

では、`2`、`6`、`8`、`8` がそれぞれ異なる位置に存在する。

そのため、Token EmbeddingだけではなくPosition Embeddingを加え、**文字そのものの情報と、系列上の位置情報を組み合わせて入力**した。

### Padding

計算結果の桁数が異なるため、バッチ学習では系列長を揃える必要がある。

そのため、`<pad>` トークンによって系列長を統一し、Loss計算では`<pad>`を無視するようにした。

## Experiment

True / Fake / Nonsense の割合を変更し、それぞれのロジックがモデルの出力にどの程度影響するかを確認した。

### True / Fake

| True | Fake | Nonsense | True correct | Fake correct | Other |
| ---: | ---: | -------: | -----------: | -----------: | ----: |
| 100% |   0% |       0% |          997 |            0 |     3 |
|  90% |  10% |       0% |          983 |            0 |    17 |
|  80% |  20% |       0% |          964 |           16 |    20 |
|  70% |  30% |       0% |          866 |           50 |    84 |
|  60% |  40% |       0% |          825 |          158 |    17 |
|  50% |  50% |       0% |          266 |          725 |     9 |

TrueとFakeの割合を近づけるにつれて、モデルの出力もそれぞれのロジックに引っ張られる傾向が確認できた。

特に50% / 50%ではFakeの正答数がTrueを上回った。

Fakeロジックは数字を連結するためTrueロジックより結果の文字数が長くなりやすく、`<pad>`をLoss計算から除外していることも含め、**系列長の違いが学習結果に影響した可能性がある。**
ただし、この仮説については今回の実験では詳細に検証していない。

### True / Nonsense

| True | Fake | Nonsense | True correct | Fake correct | Other |
| ---: | ---: | -------: | -----------: | -----------: | ----: |
|  90% |   0% |      10% |          979 |            0 |    21 |
|  80% |   0% |      20% |          958 |            0 |    42 |
|  70% |   0% |      30% |          923 |            0 |    77 |
|  60% |   0% |      40% |          913 |            0 |    87 |
|  50% |   0% |      50% |          791 |            0 |   209 |

ルールのないNonsenseの割合を増やすと、Trueの正答率は低下した。

一方で、Nonsenseそのものを正解として評価するのではなく、入力とは無関係なランダムな結果であるため、今回はNonsenseを`Other`として扱った。

### True / Fake / Nonsense

複数のロジックを混ぜた場合も比較した。

| True | Fake | Nonsense | True correct | Fake correct | Other |
| ---: | ---: | -------: | -----------: | -----------: | ----: |
|  80% |  10% |      10% |          969 |            2 |    29 |
|  60% |  20% |      20% |          867 |           34 |    99 |
|  60% |  30% |      10% |          841 |           97 |    62 |
|  60% |  10% |      30% |          860 |           16 |   124 |
|  50% |  25% |      25% |          697 |          158 |   145 |

例えばTrue 80% / Fake 10% / Nonsense 10%では、

```text
True correct    969
Fake correct      2
Other            29
```

となり、ほとんどの出力がTrueロジックとなった。

一方で、True / Fakeの割合を近づけるとFakeロジックの出力も増加した。

## What I learned

### 1. PyTorchでのモデル構築

最初はPyTorchを使ったモデル構築に難しさを感じたが、実際に層を組み合わせていくことで、Keras / TensorFlowでのモデル構築との共通点が多いことが分かった。

今回の実験を通じて、PyTorchはモデルや学習処理の各部分を明示的に設定しやすい一方、Kerasはより少ない記述でモデルを動かしやすい、という印象を持った。

### 2. Token EmbeddingとPosition Embedding

自然言語処理では、

```text
Tokenize
   ↓
ID化
   ↓
Embedding
```

という流れでトークンをベクトル化する。

Transformerでは、これに加えて**系列上の位置情報**もモデルに与える必要がある。

今回の実験では、Token Embeddingだけでは計算結果を十分に学習できなかったため、Position Embeddingを追加した。

### 3. Padding

計算結果によって文字数が変わるため、バッチとして扱うには系列長を揃える必要がある。

今回は`<pad>`を追加して系列長を統一し、Loss計算では`<pad>`を対象外とした。

### 4. `train()` と `eval()`

PyTorchでは、

```python
model.train()
model.eval()
```

によって、学習時と推論時のモデルモードを明示的に切り替える。

また、推論時には勾配計算を行わないようにしている。

### 5. 丸暗記と計算規則の一般化

今回の実験では、モデルが計算結果を丸暗記したのか、それとも足し算の規則を学習したのかを厳密には切り分けていない。

今回は小規模なモデルでの実験を目的としているため、`0～99`の数字を使った足し算データを10,000件生成した。

そのため、1桁・2桁の組み合わせが学習データにかなり多く含まれている可能性がある。

学習データに含まれない入力を十分な数用意して、未知の組み合わせへの一般化を評価する方法も考えられる。

ただし、未学習のパターンを増やすために桁数や問題設定を大きく変更すると、今回の「小規模なモデルで試験的にLLMを構築する」という目的から離れてしまう。

そのため今回は、**丸暗記と計算規則の獲得を厳密に区別していない点に留意して結果を解釈する。**

### 6. データの割合による影響

True / Fakeのように明確なルールを持つデータでは、学習データ中の割合がモデルの出力に大きく影響した。

一方、Nonsenseのようなルールを持たないデータの割合を増やした場合は、Nonsenseそのものを学習したというより、**正しいルールに基づく出力を妨げるノイズとして働いた**可能性がある。

特にTrue 80% / Fake 10% / Nonsense 10%では、Trueの正答数が969件となり、FakeやNonsenseの影響は比較的小さかった。

### 7. 小規模なLLMでも学習には多くの反復が必要

今回のモデルは足し算という非常に単純なタスクに絞った小規模なTransformerだったが、安定した出力が得られるまでに数百回程度の学習が必要だった。

回帰や分類モデルでは比較的少ないエポック数でも学習できることが多かったため、今回の実験を通じて、**言語モデルの学習が想像以上に反復的な処理を必要とすることを実感した。**

非常に単純なタスクであっても、小規模なTransformerを実際に学習させることで、LLMが大量のデータ・計算資源・学習処理を必要とする理由の一端を体感できた。

## Limitations

今回の実験には以下の制約がある。

* 小規模なTransformerを使用しており、実際のLLMとはモデル規模が大きく異なる
* 足し算という非常に限定されたタスクを扱っている
* 学習データに多くの入力パターンが含まれるため、暗記と一般化を厳密に区別できない
* Nonsenseには明確な「正解ロジック」がないため、通常の分類のように正答率を直接評価できない
* True / Fakeの出力長の違いがLossに与える影響について詳細な検証を行っていない
* 今回の結果だけから、Transformerが計算規則を「理解した」とは判断できない

## Summary

今回の実験では、小規模なTransformerを自作し、異なる計算ルールを持つデータを混ぜることで、**学習データの構成がモデルの出力にどのような影響を与えるか**を確認した。

TrueとFakeのように明確なルールを持つデータでは、データ割合が出力傾向に反映され、割合の多いロジックにモデルが引っ張られる傾向が確認できた。

一方、ルールのないNonsenseデータを増やした場合は、Nonsense自体を学習するというより、正しい計算結果を出力することを妨げるノイズとして働く傾向が見られた。

また、Token EmbeddingだけではなくPosition Embeddingを追加することで、系列上の位置情報をモデルに与える重要性も確認できた。

今回は「小規模なLLMを実際に作って動かしてみる」ことを主な目的とし、モデルの規則獲得や汎化能力を厳密に検証することまでは行っていない。

そのため、**LLMの仕組みを小さな実験に落とし込み、データ・モデル・学習方法が出力に与える影響を実際に確認するための実験**として位置づける。
